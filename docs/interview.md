# PGScope MCP 面试提纲

## 30 秒介绍

“我把 PostgreSQL 的只读查询、表结构查看和执行计划诊断封装成了本地 stdio MCP 服务，供外部 Agent 调用。服务本身不含 LLM。重点是把 SQL 限制、数据库账号权限和真实计划证据串起来，让建议可核查，也避免把估算成本误说成执行时间。”

## 实现归属与设计取舍

- **本项目实现**：五个工具的输入输出边界、SQL AST 白名单和表作用域绑定、只读连接生命周期、六类诊断规则、演示数据及可重复基准。建议只返回，不自动建索引。
- **上游依赖**：官方 MCP SDK 提供协议与 stdio 传输；SQLGlot 负责 SQL 解析；psycopg 负责 PostgreSQL 通信；执行计划、优化器成本与实测指标来自 PostgreSQL。不要把这些上游能力说成自己发明的 SQL 解析器或优化器。
- **为何不直接 fork 大项目**：需求是范围清晰的五个本地只读工具。自建薄接口更容易审计权限、输出和限制，同时仍复用成熟协议、解析器与驱动。若将来需要更广的数据库方言或工作流，再评估复用大型框架。

## 六类诊断怎么解释

| 规则 | 证据与建议边界 |
| --- | --- |
| `SELECT_STAR` | AST 投影出现 `*`；`count(*)` 不误报。建议列出需要的字段。 |
| `CARTESIAN_JOIN` | 连接缺乏匹配条件，且没有可识别的 `WHERE` 等值连接；提示确认全组合是否为本意。 |
| `SELECTIVE_SEQ_SCAN` | 大表统计估算至少 1 万行、顺序扫描带过滤且计划返回比例不超过 10%；这仍是估算，先检查统计信息。 |
| `INDEXED_COLUMN_WRAPPED` | 已有可用索引的列在过滤中被函数或 cast 包裹；建议检查可否改写谓词或评估表达式索引。 |
| `ROW_ESTIMATE_MISMATCH` | `ANALYZE` 的实际每循环行数与计划每循环估算相差至少十倍；保留 loops，避免错误相乘。 |
| `SORT_SPILL` | 实测 Sort 节点报告磁盘空间；估算 cost 高不足以证明落盘。 |

候选普通索引只覆盖简单真实单表过滤，确认列存在并检查现有索引的前导列、部分索引、表达式索引及有效性；复杂查询不生成 DDL。索引会增加写入、维护和存储成本，低选择性查询也可能继续使用顺序扫描。统计信息过旧时先 `ANALYZE`，再比较计划和实测。

## 两个真实实验怎么讲

演示库有 10 万订单。基准脚本只连接本机演示库，核对 marker 与行数，每种查询预热一次，再用 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` 测五次；前后完整结果必须一致。原始计划和每次耗时见 [基准报告](../artifacts/benchmark/benchmark.md) 与 [JSON 记录](../artifacts/benchmark/benchmark.json)。

1. **高选择性过滤**：同一 `customer_id = 42` 查询，比较无索引与创建 `orders(customer_id)` 索引。报告记录了从 `Seq Scan` 到 `Bitmap Heap Scan` / `Bitmap Index Scan` 的变化；以最新报告的五次执行时间中位数描述这台机器上的效果。
2. **谓词改写**：在 `orders(created_at)` 索引已存在时，比较 `date(created_at) = ...` 与等价的半开时间范围。报告记录了从 `Seq Scan` 到位图索引扫描的变化，耗时以最新报告为准。半开区间要与原日期语义一致，尤其留意时间类型和时区。

面试时先讲查询、索引状态、计划变化和结果一致性，再报本机五次中位数。上述倍数不是通用性能承诺；缓存、数据分布、硬件、并发和 PostgreSQL 版本都可能改变结论。`cost` 不是耗时，不能拿它计算加速比。

## 追问与下一步

- **为什么三层只读？** AST 限制常见误用，只读事务约束单次执行，数据库角色在服务之外独立限制权限；三者覆盖不同失误。只面向可信数据库，不把 SQL 白名单宣传成恶意函数沙箱。
- **为什么默认不运行 ANALYZE？** 它会执行查询；默认只取估算计划，管理员配置允许后才开放实测，诊断明确区分估算和事实。
- **怎么扩展？** 增加多列及连接谓词的保守索引评估、扩展统计信息和历史负载证据；引入更多真实计划回归样例与受控基准。任何自动建索引能力都应另设审批和回滚流程。
